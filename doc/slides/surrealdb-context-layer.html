01 · The database

What is SurrealDB?

A multi-model database written in Rust, with a SQL-family query language — SurrealQL — that speaks every model natively.

  • One engine for documents, relations, graphs, vectors and full-text search
  • One query language across all of them — joinable in a single statement
  • One transaction domain — ACID across every model
  • Any scale — embeds in your process, runs as a server, or shards across a cluster
-- one statement, three models
SELECT
  title,
  session_id.project,          -- record link (document)
  ->edge->memory.title,        -- graph traversal
  vector::similarity::cosine(
    embedding, $query_vec
  ) AS score                  -- vector math
FROM observation
WHERE embedding <|10,80|> $query_vec;
The elevator version: SurrealDB is what you get if you design a database from scratch assuming that modern applications need more than one data model, and that forcing developers to run one database per model is the actual bug. It's written in Rust. The query language, SurrealQL, deliberately looks like SQL — SELECT, WHERE, ORDER BY all behave as you expect — but it's extended with native constructs for record links, graph traversal, vector similarity, and full-text matching. The snippet on the right is a legal single statement touching three models: it reads document fields, follows a record link, walks graph edges, and ranks by cosine similarity against an HNSW index. That's the whole pitch in nine lines.
01 · The database

"Multi-model" is one engine, not a bundle.

Document

Schemaless or strict

Nested objects, arrays, typed fields — SCHEMAFULL when you want contracts, FLEXIBLE when you don't.

Relational

Tables & indexes

Typed columns, unique and composite indexes, foreign keys as first-class record<table> links.

Graph

Edges as tables

Typed relations with their own fields, traversed with ->edge->node arrows in any query.

Vector

HNSW built in

Embeddings are just array fields; KNN via the <|k,ef|> operator against a native index.

Full-text

BM25 built in

Analyzers, tokenizers, stemming and relevance scoring in the engine — no external search cluster.

The point

One transaction

All five in the same statement, same index set, same ACID commit. Nothing to sync, ever.

The bar for "multi-model": can one query, in one transaction, use all the models together? Plenty of products bolt a vector plugin onto a document store — but if the models live in different index structures with different consistency guarantees, you've just internalized the sprawl. In SurrealDB each of these is native: HNSW and BM25 are index types exactly like a unique index, edges are tables, and everything commits atomically together. Hold the "one transaction" cell in your head — it's what makes the agent story in act four work.
01 · The database

What it replaces.

Left side is a real architecture — I've seen this exact diagram in multiple agent-memory posts, and it's what most memory frameworks assume underneath. The orange dashed lines are the part that hurts: every pair of stores that must agree needs a sync path, and every sync path is a place where your agent's knowledge forks. When the vector store returns a memory that the graph store already superseded, the agent confidently acts on stale context — that class of bug simply cannot exist when there is one store. The right side is not "five databases in a trench coat": it's one storage engine, one query planner, one transaction log, in which these five are index types and query operators.
01 · The database

That takes solving two hard problems.

Two hard problems, and they're independent. Problem one is the language: SQL has no words for "nearest neighbours" or "walk this edge" — so most databases bolt those on as function calls, and it shows. SurrealQL extends the grammar itself; act two walks through it operator by operator. Problem two is scale: the engine that's perfect inside a laptop process is the wrong design for a hundred-node cluster. SurrealDB's answer is one query engine over swappable storage — act three. These two problems are the skeleton of the talk.

02 · The query layer

SurrealQL 101 — the primary key is a pointer.

  • Every record id is table:id — a value you can store in another record
  • Following a stored id is a dot — no JOIN
  • The rest is SQL: SELECT, WHERE, ORDER BY work as you expect
-- a record, with its id chosen by you
CREATE person:tobie SET
  name = 'Tobie',
  company = 'SurrealDB';

-- SurrealQL: one line
SELECT friend.name FROM person:tobie;

-- classic SQL: a join
SELECT f.name FROM person p
JOIN person f ON p.friend_id = f.id
WHERE p.id = 'tobie';
Thirty seconds of orientation. Record ids are written table-colon-id, and the id is a value — store it in a field of another record and the engine can follow it directly. That's what the one-liner does: friend holds a person id, and dot-name dereferences it. Below it, the same question in classic SQL needs a join. Everything else in the language behaves like the SQL you already know.
02 · Model 1 of 4 — document

Document: strict where you want, open where you don't.

-- a strict table: fields are typed and checked
DEFINE TABLE user SCHEMAFULL;
DEFINE FIELD name  ON user TYPE string;
DEFINE FIELD email ON user TYPE string
  ASSERT string::is_email($value);

-- one open field inside the strict table
DEFINE FIELD settings ON user
  TYPE object FLEXIBLE;
-- nested data goes straight in…
CREATE user SET
  name  = 'Jaime',
  email = 'jaime@example.com',
  settings = {
    theme: 'dark',
    beta: { flags: ['a', 'b'] }
  };

-- …and queries with a dot path
SELECT settings.theme FROM user;

The engine validates name and email. settings takes any shape. One table, both behaviours.

Model one: documents. A SCHEMAFULL table is a contract — fields are typed, and ASSERT runs a check on every write, like the email validation here. But real data always has one corner that won't sit still, so a single field can be declared FLEXIBLE: any nested shape goes in, and dot paths query it. You choose strictness per field, not per database.
02 · Model 2 of 4 — relational

Relational: constraints, indexes, aggregation.

-- uniqueness, enforced by the engine
DEFINE INDEX unique_email
  ON TABLE user FIELDS email UNIQUE;

-- composite: one person, one review per article
DEFINE INDEX one_review
  ON TABLE review
  FIELDS person, article UNIQUE;
-- and plain SQL aggregation
SELECT
  company,
  count() AS people
FROM person
GROUP BY company;

The unglamorous parts — uniqueness, ordering, counting — work the way SQL taught you.

Model two, on purpose the boring one: constraints and aggregation. A unique index rejects duplicates at write time; a composite unique index enforces rules like "one review per person per article". GROUP BY and count behave exactly as in SQL. If a database wants to hold a system of record, these have to work — and they do, in the same engine as everything that follows.
02 · Interlude — record links

Record links: store an id, follow it with a dot.

-- store record ids like any other value
CREATE person:jaime SET
  name = 'Jaime',
  friends = [person:tobie, person:simon];

-- follow them in a query — no join
SELECT friends.name FROM person:jaime;

-- ["Tobie", "Simon"]
The bridge from documents to graphs. friends holds two record ids — actual addresses, not foreign keys to join on. friends-dot-name follows both and returns the names, in one query, one line. When ids are pointers, the next question is obvious: what if the connection itself needs data — when it was made, how strong it is? That's the graph model.
02 · Model 3 of 4 — graph

Graph: relations you can walk.

-- connect two records with a named relation
RELATE person:aristotle->wrote->article:on_sleep
  SET at = time::now();

-- walk forward: what did he write?
SELECT ->wrote->article.title
FROM person:aristotle;

-- walk backward: who wrote this?
SELECT <-wrote<-person.name
FROM article:on_sleep;
Model three: graph. RELATE connects two records with a named relation — person wrote article — and the arrow syntax walks it: forward for "what did he write", backward for "who wrote this". The relation is itself a record, so it carries fields — here, when it was written. No separate graph database, no separate query language. In act five you'll see hifz use exactly this to connect memories to the code they describe.
02 · Model 4 of 4 — vector

Vector: an index type, a query operator.

-- an HNSW index on an array field
DEFINE INDEX idx_embedding ON article
  FIELDS embedding
  HNSW DIMENSION 384 DIST COSINE;

-- the 5 nearest neighbours of a vector
-- (5 = how many · 40 = search effort)
SELECT title FROM article
WHERE embedding <|5,40|> $query_vector;
Model four: vectors. Two statements, that's the whole feature. An embedding is an ordinary array field; HNSW is an index on it, declared with a dimension and a distance metric — exactly the way you'd declare a unique index. Retrieval is the bracket operator: five nearest neighbours, search effort forty. Because it runs inside the query engine, the result can be filtered, joined, or graph-walked in the same statement — no separate vector database, and the embeddings can never drift from the rows they belong to.
02 · Bonus model — full-text

Full-text: BM25 relevance in the engine.

-- how text becomes searchable terms
DEFINE ANALYZER simple
  TOKENIZERS blank
  FILTERS lowercase, snowball(english);

-- a BM25 index on a field
DEFINE INDEX idx_title ON article
  FIELDS title
  FULLTEXT ANALYZER simple BM25;

-- match and rank ("1" pairs the two)
SELECT title, search::score(1) AS score
FROM article
WHERE title @1@ 'sleep'
ORDER BY score DESC;
Vectors find meaning; full-text finds exact words — error strings, names, identifiers — which similarity search reliably misses. The analyzer declares how text becomes terms: split, lowercase, stem. The index adds BM25 relevance scoring. In the query, the at-one-at operator matches through index number one, and search-score-one returns that match's relevance — the number simply pairs a match with its score when a query uses several indexes at once. That pairing is what makes the next slide possible.
02 · Combining models

Hybrid search: two retrievers, one query.

-- vector search and keyword search,
-- merged by rank
search::rrf([

  (SELECT id FROM article
   WHERE embedding <|10,40|> $query_vector),

  (SELECT id, search::score(1) AS s
   FROM article WHERE title @1@ $q
   ORDER BY s DESC LIMIT 10)

], 10);  -- top 10 overall
  • One branch finds meaning, the other finds exact words
  • search::rrf merges them by rank — no score-normalisation code
  • In a split stack this is two systems and a merge service

hifz runs this with three branches in production — act 05.

The models combine. Hybrid retrieval — semantic plus keyword — is the standard recipe for good recall, and here it's one function: two sub-queries as branches, one KNN, one BM25, fused by reciprocal rank. Merging by rank instead of by score matters: cosine similarities and BM25 scores aren't comparable numbers, but ranks always are. In a split stack this is two services, two result sets, and normalisation code you have to write and maintain. hifz's production version adds a third branch — you'll see it in act five.
02 · The query layer

And all of it is transactional.

-- the documentation's own example
BEGIN TRANSACTION;

CREATE account:one SET balance = 135605.16;
CREATE account:two SET balance = 91031.31;

UPDATE account:one SET balance += 300.00;
UPDATE account:two SET balance -= 300.00;

COMMIT TRANSACTION;
  • Every statement so far — CREATE, RELATE, vector writes, index updates — can share one transaction
  • All of it commits, or none of it does
  • LIVE SELECT * FROM article; — and any table can be subscribed to as it changes
Before leaving the language: it's a database first. The docs' own example — move money between two accounts, atomically. The point for us: a document write, a graph edge, and the vector index update they trigger can all sit inside one transaction. When act five stores a memory and links it to code, that's one atomic commit — which is exactly what a split stack cannot give you. And LIVE SELECT turns any query into a subscription; the hifz dashboard uses it instead of polling.

Act three: the storage layer. This is the less visible half of the multi-model promise but, for anyone shipping products, arguably the more valuable one. The question it answers: why should the database you prototype with be a different product from the database you scale with?
03 · The storage layer

One compute layer, pluggable engines.

The architecture that makes scale-portability possible: everything from act two — the parser, the planner, HNSW, BM25, permissions — lives in a compute layer that talks to storage through one narrow contract: a transactional key-value interface. Give me ordered keys, versioned reads, atomic commits — and the engine doesn't care what's underneath. That contract is implemented by radically different engines: IndexedDB in a browser tab, a lock-free in-memory store, embedded LSM trees, RocksDB on a server, raft-replicated nodes across a cluster. Your schema, queries, and indexes are identical across all five columns. Let me take you through the three engines SurrealDB builds itself.
03 · Engine 1 of 3

surrealmx — in-memory, lock-free.

An embedded, in-memory, lock-free, transactional KV engine — built for workloads where latency is the feature.

  • Lock-free MVCC — concurrent readers and writers, no blocking
  • Serializable & snapshot isolation — real transactions, in RAM
  • Optional durability — append-only log + periodic snapshots, fsync per-commit or in background
Where it fits

Hot context, ephemeral state

Session caches, test suites, agent scratch space — anything where you'd otherwise bolt on Redis, but want SurrealQL, vectors and transactions over it.

  • github.com/surrealdb/surrealmx
  • apache 2.0 · crates.io
  • optional AOL + LZ4 snapshots
Engine one: surrealmx, the in-memory engine. The headline is lock-free multi-version concurrency control — multiple readers AND multiple writers making progress simultaneously without lock contention, with serializable and snapshot-isolated transactions on top. In-memory does not mean throwaway: you can attach an append-only log with per-commit or background fsync, plus periodic compressed snapshots — a spectrum from pure cache to fully durable. In the agent story, this is the tier that replaces the Redis box from slide two: your hot working state gets the same query language and transaction semantics as your long-term memory.
03 · Engine 2 of 3

surrealkv — embedded, versioned, time-travelling.

A persistent, embedded LSM-tree store, written in Rust to evolve with SurrealDB's own access patterns — and to shed the RocksDB dependency.

  • MVCC snapshot isolation — non-blocking concurrent reads and writes
  • Built-in versioning — point-in-time reads, historical queries
  • WiscKey-style value log — large values stored off-tree, with GC
  • Checkpoint & restore — consistent snapshots for backup
// hifz: crates/kernel/src/db.rs —
// the entire "deploy a database" story
pub async fn connect(path: &str)
    -> Result<Surreal<Db>> {
  let db = Surreal::new::<SurrealKv>(path).await?;
  db.use_ns("hifz").use_db("main").await?;
  Ok(db)
}

the database is a rust crate — no server, no port, no ops

Engine two: surrealkv, the embedded persistent engine, and the one hifz ships on. LSM-tree architecture, snapshot-isolated MVCC, and two features that matter for memory systems specifically. First, native versioning with time-travel reads — the storage layer itself can answer "what did this record look like last Tuesday", which for an agent memory is provenance for free. Second, a WiscKey-style value log that keeps large values off the tree — relevant when your rows carry kilobyte-scale embeddings and narratives. And look at the code: that function is hifz's entire database deployment. Six lines. It's a crate, not a service — the full act-two engine, HNSW and BM25 included, inside your process writing to one directory.
03 · Engine 3 of 3

surrealds — the distributed tier.

SurrealDB's own distributed storage tier. Same KV contract as the embedded engines — implemented by a cluster.

  • Consensus-replicated storage nodes — lose a node, keep the data
  • Local-disk speed, object-storage durability — hot data stays close, durability lands in cloud storage
  • Prefer an existing distributed KV? TiKV implements the same interface
Engine three: surrealds, the distributed tier — same KV contract, now implemented by a cluster. Nodes replicate through consensus, and the design separates performance from durability: hot data lives on each node's local disk, so the latency profile stays local, while durability lands in object storage — lose a node's disk and it re-hydrates. That's the shape modern cloud databases converge on. If you're already invested in TiKV, it implements the same interface. The point for this talk isn't cluster internals — it's that the top half of the diagram never changed.

Act four. We leave the database for a moment and talk about agents — specifically about what the "context layer" everyone is naming actually has to do. 04 · The problem

Your agent learns for one session, then forgets.

The context window is working memory. Fast. Rich. Wiped every session. What evaporates:

  • The decision you debated for an hour and settled
  • The root cause of the bug it just fixed
  • Your project's conventions — re-derived, wrongly, tomorrow
  • The three approaches that failed — about to be tried again
Everyone in this room has felt the sawtooth. Session one, the agent ramps up on your codebase, makes real progress — and at the cutoff, everything above the axis is gone. Session two starts from zero, re-reads the same files, re-asks the same questions, sometimes re-attempts the same failed fix. Bigger context windows don't fix this — they just make the teeth taller; the reset still comes, and cost scales with everything you re-feed. The lime curve is what we actually want: knowledge that compounds. The difference between the two curves is not a smarter model — the model is identical. It's persistence.
04 · The anatomy

A context layer is five verbs and a lifecycle.

Five verbs. Capture: hook the agent loop, record what happened — tool calls, edits, decisions. Compress: shrink raw events to a title, facts and keywords, then embed. Store. Recall: given the task, retrieve the top-k most useful things. Inject: fit them into the token budget. The part everyone underestimates is the black band: memory is a lifecycle, not append-only storage. Facts decay. Useful ones get reinforced. Contradictions supersede, history preserved. This band is what separates a context layer from a logging pipeline — and every verb in it is a database operation.

04 · The stakes

Retrieval quality is agent quality.

agent quality = retrieval precision × ranking(similarity, relevance, recency, graph)
Scarcity

Tokens are the budget

Noisy recall is worse than no memory.

Precision

Wrong memory, wrong action

Lifecycle is a correctness feature.

Ranking

Every signal, one query

Each signal lives in a different model.

Last framing slide, on why this is worth engineering carefully. Memory is not free context — it competes for the same window as code and reasoning, so a retriever with poor precision actively degrades the agent. Worse, memory is authoritative to the model: recall a decision that was reversed last month and the agent doesn't hedge, it acts. So the ranking function has to combine signals — is it about this? does it mention this exact identifier? is it connected to what else matters now? is it fresh? has it proven useful? Each signal comes from a different data model. When those live in one engine, that ranking is a query. When they don't, it's a distributed system. Now let me show you the running version.

05 · The story

The trail behind one fix.

Here's the whole story on one picture — the next slides just zoom in. An issue arrives: CI auth tests are flaky. A long session of commands follows — and somewhere in the middle, Claude's context compacts; the window forgets, but the log hifz keeps does not. The investigation becomes a plan, the plan becomes commit 9f2c1a touching src/auth.rs, and the lesson is saved. Weeks later a new session asks why token refresh is written this way — and the lesson, the plan, and the exact lines come back. Three moves: store the work, link it to the code, get it back — two slides each.

05 · Move 1 of 3

Store the work.

hook fires → shrunk to title + facts → embedded locally → stored — one row

Every command the agent runs fires a hook. Each hook stores one row.

  • Read, Bash, Edit — each becomes an observation
  • Long output is shrunk to a title and facts before it's embedded
-- what the hook stores for one command
CREATE observation SET
  session_id = session:s1,
  obs_type   = 'command_run',
  title      = 'cargo test auth — 4 failures',
  files      = ['tests/auth.rs'],
  embedding  = $vec;  -- embedded locally

one row per command · searchable by meaning and by words, instantly

Move one: store the work. Claude Code fires a hook on every event; each hook posts to hifz, which shrinks the output to a title and facts, embeds it locally, and stores one observation row — that's the strip at the top, and it's the entire write path. The row you see is observation o1: cargo test auth, four failures, tests/auth.rs. Because the vector index and the text index are indexes on this same table, the row is searchable both ways the moment it lands. One row per command, for the whole session.

05 · Move 1 of 3

The window forgets. The log doesn't.

Mid-session, Claude's context compacts. PreCompact/PostCompact hooks store the summary as one more row — ord and parent_obs_id keep the causal chain.

-- the compaction summary is just another row
CREATE observation SET
  session_id    = session:s1,
  obs_type      = 'post_compact',
  title         = 'summary: suspect token refresh
                   timing under CI load',
  parent_obs_id = observation:o46;
                  -- the chain continues

a record link, not a join table — parent_obs_id points straight at the previous row

This is why the capture layer exists. Forty-odd commands in, Claude's context window compacts — older turns are replaced by a short summary and the window moves on. hifz hears about it through the PreCompact and PostCompact hooks and stores the summary as observation o47: suspect token refresh timing under CI load. It's just another row, but parent_obs_id — a record link from act two — points at o46, so the causal order survives. The window forgets; the log doesn't.

The agent that executes the plan tomorrow doesn't have to be the one that wrote it today.

Move two begins where the investigation ends: a plan. It's saved as a memory with category plan and status active — one CREATE, nothing new. But active status changes its behaviour: from now on, every session's warmup briefing carries it, until it's marked done. That matters because the session that wrote the plan and the session that executes it are often not the same session — the plan is the hand-off. Next: the execution, and linking what shipped.

05 · Move 2 of 3

Link it to the code.

-- the lesson, saved after commit 9f2c1a
CREATE memory:auth_race SET
  title   = 'Token refresh race caused
             flaky CI auth tests',
  content = 'CI machines are slower; tokens
             expired mid-request. Fix: refresh
             before the expiry window.',
  files   = ['src/auth.rs'];

-- linked to the code, and to the work
RELATE memory:auth_race->references->code_chunk;
                              -- src/auth.rs:142
RELATE memory:auth_race->generated_by->run;
The plan is executed, and commit 9f2c1a lands — code is the ground truth. The hook detects the commit, the lesson is saved as memory auth_race, and RELATE — the graph operator from act two — connects it to the code chunk it describes and to the run that produced it. Now the trail is a graph: issue, plan, commit, code, lesson, all connected. And the commit does one more thing: it separates real work from noise — memories about committed files are kept and strengthened, while work that never shipped fades out after sixty days.

Move three: get it back — and the first half is plumbing worth seeing, because this is the whole Claude Code integration. At session start, a hook fetches a fifteen-memory briefing — the active plan, recent lessons, recent work on shop-api — and prints it; Claude Code prepends whatever a SessionStart hook prints. Then on every prompt, the UserPromptSubmit hook runs a search on the prompt text and returns matches in the additionalContext field. Two small scripts; no prompt engineering, no framework. The new session knows about the auth fix before its first token.

05 · Move 3 of 3

The question comes back with the code.

-- "Why is token refresh written this way?"
search::rrf([
  (SELECT id FROM memory
   WHERE embedding <|20,80|> $question),
                        -- by meaning
  (SELECT id FROM memory
   WHERE content @1@ 'token refresh')
                        -- by exact words
], 10);

-- one graph hop from the winners:
SELECT ->references->code_chunk,
       <-generated_by<-run FROM $found;
What comes back
  • the lesson — "Token refresh race caused flaky CI auth tests"
  • the plan — "refresh tokens before the expiry window"
  • the code — src/auth.rs:142-198 · refresh_token

Not just an answer — the decision, and the lines it produced. Newer and more-used memories rank higher.

The second half of move three: the agent asks why token refresh is written this way. One query — the hybrid form from act two: a vector branch for meaning, a keyword branch for the exact words "token refresh", merged by reciprocal rank fusion. Then one graph hop from the winners, following references to the code chunk and generated_by back to the run. What comes back is the lesson, the plan behind it, and src/auth.rs lines 142 to 198 — the decision and the ground truth together. Ranking favors newer and more-used memories, so recall stays current.
05 · Background

Left alone, it tidies up.

One background job keeps the store from silting up. In: a week of raw observations. Four passes: similar observations get merged into one fact by a local LLM; related memories get linked by keyword overlap — plain math; workflows that keep repeating become step-by-step procedures; and facts nobody uses fade — strength times zero-point-nine per pass, deleted below a threshold. Out: fewer, stronger rows. No fine-tuning, no training loop, no GPU. Each pass is idempotent, so it can run on a schedule.

05 · The same recipe · code

The codebase is indexed too.

Code is the ground truth — so the same three moves apply to the repository itself.

store

tree-sitter splits 8 languages on function boundaries; each chunk is embedded and text-indexed

link

lesson → code references edges re-anchor as lines move

the same hybrid query, filtered language = 'rust'

-- one chunk = one function
CREATE code_chunk SET
  path       = 'src/auth.rs',
  start_line = 142,
  end_line   = 198,
  symbols    = ['refresh_token'],
  embedding  = $vec;

a file watcher re-indexes on save — the index follows the code

The three moves generalise, first to the code itself — since code is the output of every plan, hifz indexes the repository. Store: tree-sitter splits eight languages on function boundaries, and every chunk gets the same row shape you've been seeing — here, src/auth.rs lines 142 to 198, symbol refresh_token, plus an embedding. Link: the references edges from move two point at these chunks, and they re-anchor when lines move. Get back: the same hybrid query, filtered to language rust. A file watcher re-indexes on save, so the index never drifts from the code.

Act six · where this goes

hifz builds memory on the database.
What if memory lived in it?

Everything in act five — decay, linking, consolidation, versioning — is application code built on database primitives. The next question is whether those belong in the database itself.

Last act, and a genuine open question rather than a pitch. Look back at what hifz is: SurrealDB supplies the models and the transactions, and a few thousand lines of Rust turn them into memory semantics — decay schedules, link channels, consolidation tiers. It works. But notice the shape: all of that logic is generic. Nothing about "memories decay" or "contradictions supersede" is specific to my app. When application logic is that universal, it usually migrates down into the platform — the way full-text search migrated from Lucene sidecars into the database. So: what would it look like if memory semantics lived in the database itself?
06 · What we're exploring

Spectron: memory semantics as substrate.

A research direction at SurrealDB. Knowledge. Lived experience. Reasoning traces. One transactional substrate — where the database itself understands memory.

  • Reconciliation — authoritative documents and lived observations merge under one trust model, in one transaction
  • Elaboration — inferred links across entities, computed differentially, not in batch jobs
  • Reflection & consolidation — the store thinks while the agent is away: traces become memory, repetition becomes belief
  • Calibration — every assertion carries confidence; memory that knows what it doesn't know
Spectron is that exploration. The framing: an agent's mind has three kinds of content — knowledge it was given, experience it lived, and reasoning it performed — and today those are reconciled by application code, if at all. Spectron pushes the semantics down: reconciliation with a trust model, so documentation supersedes hearsay atomically; elaboration that infers new links differentially as facts arrive; reflection and consolidation as background processes — the store literally thinks between sessions; and calibration, where every assertion carries confidence, so the memory can say "I don't know" instead of hallucinating. I'm showing you the ladder deliberately: bottom rung is where the industry is, hifz is the middle rung and you can build it today, Spectron is the rung we're exploring. 06 · Takeaways

Three things to take home.

01

Multi-model removes the glue tier

One engine. One query language. One transaction. No drift.

02

Storage spans scale

Browser to cluster on one schema. No rewrites. Nothing about your data model is disposable.

03

Context is a database problem

RAG, GraphRAG, hybrid search, lifecycle — all schema. hifz is the existence proof.

Three takeaways. One: multi-model is not a convenience feature — it eliminates the glue tier, which is where agent memory systems actually fail. Two: the storage spectrum means your data model outlives your deployment story — browser to laptop to cluster on one schema. Three, the thesis of the talk: the context layer is a database problem, and when the database is multi-model, it's a *small* database problem.
